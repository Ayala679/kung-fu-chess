# Kung Fu Chess - הסבר כללי על הפרויקט

מסמך זה נותן תמונה כללית של הפרויקט: מה זה בכלל, איך הוא בנוי, ואיך הוא התפתח מתוכנת שחמט מקומית פשוטה לשרת מבוזר עם כמה תהליכים. הפרטים הטכניים לעומק נמצאים בשני קבצים נוספים:

- `02_game_engine_deep_dive.md` - איך מנוע המשחק עצמו עובד (הכללים, הזמן-אמת, הקפיצות)
- `03_networking_deep_dive.md` - איך השרת המבוזר עובד (כל התהליכים, Redis, NATS, Docker)

---

## 1. מה זה Kung Fu Chess בכלל?

זהו מימוש ב-Java של גרסת שחמט "בזמן אמת" (Real-Time Chess), בהשראת המשחק "Kung Fu Chess" האמיתי. ההבדל המהותי משחמט רגיל:

- **אין תורות.** בשחמט רגיל שחקן לבן זז, אחר כך שחור, וכן הלאה. כאן שני הצדדים יכולים לזוז **בו-זמנית**, בכל רגע נתון.
- **מהלך לוקח זמן אמיתי.** כלי לא "קופץ" מיד מריבוע לריבוע - הוא **נע** על הלוח באנימציה אמיתית, ולוקח זמן ממשי (מילישניות) עד שהוא מגיע ליעד. כלי כבד יותר (למשל מלכה) יכול לנוע מהר יותר או לאט יותר מכלי אחר, בהתאם לחוקי המשחק.
- **אפשר "לקפוץ" כדי להתחמק.** אם כלי בסכנת אכילה, השחקן יכול ללחוץ קליק ימני כדי לגרום לכלי "לקפוץ" במקום (לא לזוז לריבוע אחר) - אם הקפיצה מתוזמנת נכון, הכלי התוקף "מפספס" והכלי שקפץ נשאר בחיים ברגע שהוא נוחת בחזרה.
- כתוצאה מזה, יש כאן אלמנט אמיתי של **תזמון וריאקציה** - לא רק חשיבה אסטרטגית כמו בשחמט רגיל, אלא גם רפלקסים.

המשחק מיושם כך שאפשר לשחק אותו בשלוש דרכים:
1. **קונסולה (טקסט)** - לצורך בדיקות אוטומטיות, אין ממשק גרפי.
2. **גרפי מקומי** - חלון Swing (ספריית GUI סטנדרטית של Java), שני שחקנים על אותו מחשב.
3. **גרפי ברשת** - כמו למעלה, אבל שני שחקנים מתחברים משני מחשבים שונים לשרת משותף, כולל חשבונות משתמש, דירוג (ELO), מצב המתנה, חדרים, וכו'.

## 2. איך הפרויקט בנוי (ברמת הקוד)

אין כאן כלי בנייה כמו Maven או Gradle (נפוצים בפרויקטי Java) - הכל מתקמפל ישירות עם הפקודה `javac` (המהדר הרגיל של Java), וקובץ בשם `sources.txt` מפרט בדיוק אילו קבצי קוד לכלול. ספריות חיצוניות (למשל הספרייה שמטפלת ב-WebSocket) מורדות פעם אחת לתיקיית `lib/` דרך סקריפט PowerShell.

**שכבות הקוד** (חלוקה לפי אחריות - כל שכבה יודעת רק על השכבה שמתחתיה):

```
קלט (עכבר/מקלדת/רשת)
        │
        ▼
  event/          - מתרגם קלט לפעולה ("קליק על משבצת (3,4)")
        │
        ▼
  gameengine/      - "המוח" של המשחק: מקבל בקשות מהלכים,
                     בודק חוקיות (דרך ruleengine/), ומנהל את
                     הזמן-אמת (מהלכים בתנועה, קפיצות, התנגשויות)
        │
        ▼
  model/           - הנתונים הגולמיים: הלוח, הכלים, המיקומים
        │
        ▼
  snapshot/        - "צילום מסך" בלתי-ניתן-לשינוי של מצב המשחק
        │
        ▼
  view/            - ציור על המסך (או, ברשת: שליחה ללקוח מרוחק)
```

בנוסף יש `parsing/` (המרה בין טקסט ללוח), `ruleengine/` (רק בודק אם מהלך חוקי - לא יודע כלום על זמן), ו-`controller/` (מחבר הכל יחד לפקודה אחת שאפשר להריץ).

**הרעיון המרכזי**: `gameengine.GameEngine` הוא ה"שער היחיד" לכל פעולה במשחק - כל מי שרוצה להזיז כלי, לקפוץ, לבדוק אם המשחק נגמר וכו', פונה רק אליו. זה נכון גם למשחק מקומי (קונסולה/GUI) וגם למשחק ברשת - **אותו מנוע משחק בדיוק** משמש בשני המקרים. השרת לא "ממציא" גרסה משלו לחוקי המשחק.

## 3. איך הפרויקט התפתח - ציר זמן

הפרויקט התחיל כמשחק שחמט-בזמן-אמת רגיל, **מקומי בלבד** (בלי רשת בכלל) - שני שחקנים על אותו מחשב, אותו חלון. השלב הזה כולל את כל מה שמתואר בקובץ `02_game_engine_deep_dive.md`.

אחר כך התווספה **רשת** - אפשרות לשני שחקנים לשחק ממחשבים שונים, עם שרת מרכזי. זה כולל: הרשמה/התחברות, דירוג ELO, "משחק מהיר" (quick match) שמתאים יריבים לפי דירוג, חדרים עם קוד (למשחק מול חבר), צופים, טיפול בניתוק/התחברות-מחדש, ולוגים.

לאחר מכן, במסגרת משימה אקדמית ("CTD 26"), הצוות המנחה ביקש לבנות את השרת בצורה **מבוזרת** יותר - במקום תהליך אחד שעושה הכל, לפצל אותו לכמה **תהליכים נפרדים** שכל אחד אחראי על משהו אחר, לפי תרשים ארכיטקטורה של 6 רכיבים:

| # | רכיב | תפקיד |
|---|---|---|
| 1 | **API Gateway** | REST רגיל (לא בזמן אמת) - התחברות, הרשמה, יצירת חדרים |
| 2 | **WS Gateway** | חיבורי WebSocket חיים (בזמן אמת) - קליקים, קפיצות, עדכוני מצב |
| 3 | **Matchmaker** | מתאים בין שני שחקנים למשחק מהיר לפי דירוג |
| 4 | **Game Allocator** | מחליט **לאיזה** שרת-משחק (shard) לשלוח כל room חדש |
| 5 | **Game Server Shards** | השרתים שבפועל מריצים את מנוע המשחק - אפשר שיהיו כמה, כל אחד עם החדרים שלו |
| 6 | **Observability** | לוגים, מטריקות, בדיקת תקינות, בדיקות עומס |

לצורך התקשורת בין כל התהליכים האלה משתמשים ב-**NATS** (מערכת הודעות בין-תהליכית - כמו "לוח מודעות" שתהליך אחד מפרסם עליו הודעה, ותהליך אחר קורא אותה), **Redis** (מסד נתונים מהיר לזיכרון זמני/משותף - למשל "מי מחובר עכשיו", "איזה room שייך לאיזה shard"), ו-**PostgreSQL** (מסד נתונים "אמיתי" וקבוע - חשבונות משתמשים ודירוג). כל זה רץ יחד דרך **Docker Compose** - כלי שמריץ כמה תהליכים, כל אחד ב"קופסה" (container) משלו, בפקודה אחת.

**החלטה ארכיטקטונית חשובה שחוזרת שוב ושוב בפרויקט**: כל רכיב שעבר "לענן" (Redis/NATS/Postgres) בנוי כך שיש לו **שני מימושים** - אחד "מקומי" (In-Memory, בזיכרון של אותו תהליך, בלי צורך בשום שירות חיצוני) שמשמש כל בדיקה אוטומטית (test) והרצה מקומית פשוטה, ואחד "אמיתי" (מבוסס Redis/NATS/Postgres) שמשמש רק כשבאמת מריצים את המערכת המבוזרת המלאה עם Docker. זה מאפשר לפתח ולבדוק הכל **מהר, בלי Docker בכלל**, ורק כשרוצים להריץ "בגדול" - עוברים למימוש האמיתי, בלי לשנות שורת קוד אחת בלוגיקה עצמה.

### מצב נוכחי (מה שכבר בוצע)

1. ✅ שרת בסיסי ברשת (WebSocket, חשבונות SQLite, ELO, matchmaking, חדרים, ניתוק/חיבור מחדש)
2. ✅ REST API + PostgreSQL + Docker Compose
3. ✅ Redis (מצב משותף) + NATS (ערוץ תקשורת פנימי)
4. ✅ API Gateway כתהליך נפרד
5. ✅ WS Gateway כתהליך נפרד מ-Game Server Shard, ו-**Matchmaker** גם כתהליך נפרד משלו
6a. ✅ **Game Allocator** + **כמה** Game Server Shards (כרגע 2) - כולל כל בעיית הניתוב שזה יוצר
6b. ⬜ Observability - עדיין לא בוצע (יש רק לוג טקסט בסיסי)
6c. ⬜ Kubernetes/K3s - עדיין לא בוצע (יש רק Docker Compose)

הפרטים המלאים של כל שלב (כולל דוגמאות זרימה קונקרטיות, מה כל תהליך עושה בדיוק, ואיך פותרים את בעיית "לאיזה שרת לשלוח את הפקודה") נמצאים ב-`03_networking_deep_dive.md`.
