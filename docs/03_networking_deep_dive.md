# עומק - איך השרת המבוזר עובד

מסמך זה מסביר לעומק את כל שכבת הרשת - מהשלב הכי בסיסי (שני שחקנים מתחברים לשרת אחד) ועד המצב הנוכחי (שישה סוגי תהליכים נפרדים, שניים מהם רצים כמה פעמים, מתואמים דרך Redis ו-NATS, בתוך Docker). מניח שקראת את `01_overview.md`. למנוע המשחק עצמו (שלא משתנה בין מקומי לרשת) ראו `02_game_engine_deep_dive.md`.

---

## חלק א': מושגי יסוד (בשביל מי שצריך רענון)

- **WebSocket** - חיבור רשת "פתוח וחי" בין לקוח לשרת: שני הצדדים יכולים לשלוח הודעות בכל רגע, בלי לפתוח חיבור חדש בכל פעם. מתאים למשחק בזמן אמת - השרת יכול לדחוף עדכון ("הכלי זז") ללקוח בלי שהלקוח "יבקש" את זה במפורש.
- **REST / HTTP** - הדרך ה"קלאסית" לתקשר עם שרת: הלקוח שולח בקשה אחת (למשל "תחבר אותי"), השרת עונה, והחיבור נסגר. מתאים לפעולות חד-פעמיות שלא צריכות זרם חי - התחברות, הרשמה, יצירת חדר.
- **פרוטוקול** - "שפה" מוסכמת בין לקוח לשרת. כאן זה טקסט פשוט מופרד ברווחים (`"click 3 4"`) או בקו אנכי (`"WELCOME|role=WHITE"`), לא JSON - בחירה מכוונת כדי לא להוסיף תלות חיצונית מיותרת.
- **Pub/Sub (Publish/Subscribe)** - דפוס תקשורת: תהליך אחד "מפרסם" הודעה על "נושא" (topic/subject) מסוים, וכל תהליך אחר שנרשם ("subscribe") לאותו נושא מקבל אותה. אף אחד לא צריך לדעת מראש **מי בדיוק** יקבל את ההודעה - זה מה שמאפשר לתהליכים להיות באמת עצמאיים זה מזה.
- **NATS** - מערכת Pub/Sub אמיתית (שרת נפרד) שמשמשת כ"לוח מודעות" בין כל התהליכים בפרויקט. תומכת גם ב-"Request/Reply" - תהליך שולח בקשה על נושא מסוים ומחכה לתשובה ספציפית (כמו טלפון, לא כמו לוח מודעות).
- **Redis** - מסד נתונים מהיר שיושב כולו בזיכרון (RAM), מתאים לנתונים ש"חיים קצר" וצריכים גישה מהירה - למשל "מי מחובר עכשיו עם איזה טוקן", "לאיזה room מסוים שייך המשתמש הזה". לא מתאים לנתונים שחייבים להישמר לתמיד.
- **PostgreSQL** - מסד נתונים "רגיל", קבוע - כאן משמש רק לחשבונות משתמשים ודירוג ELO.
- **Docker / Container** - "קופסה" קלה שמריצה תוכנית אחת (למשל תהליך Java אחד) מבודדת מהמערכת שסביבה, עם בדיוק מה שהיא צריכה כדי לרוץ. **Docker Compose** מתאר קובץ אחד (`docker-compose.yml`) שמפרט כמה קופסאות כאלה צריך להריץ יחד ואיך הן מתחברות זו לזו, ומריץ את כולן בפקודה אחת.
- **דירוג ELO** - שיטת ניקוד סטנדרטית (משחמט אמיתי) לדרג שחקנים לפי כישרון - כל ניצחון/הפסד מזיז את הדירוג של שני הצדדים, כמה שיותר משמעותית ככל שההפרש בדירוג ההתחלתי גדול יותר (ניצחון נגד מישהו מדורג גבוה יותר "שווה" יותר).

## חלק ב': לפני ה"פיצול" - איך רשת עבדה בהתחלה

לפני שהתחילו לפצל לתהליכים נפרדים, **תהליך Java אחד** עשה הכל: קיבל חיבורי WebSocket, ניהל חשבונות, ניהל חדרים, הריץ את מנוע המשחק, הכל באותו JVM (תהליך Java).

### server.GameSession - "משחק אחד"

`GameSession` מייצג משחק בודד: לוח + מנוע (`GameEngine`, אותו מנוע בדיוק מ-`02_game_engine_deep_dive.md`), עד שני שחקנים מושבים (לבן/שחור) ועוד צופים (viewers) כמה שרוצים, ו-**"טיקר" (ticker)** משלו - חוט (thread) שמריץ `advanceTime(16)` כל 16 מילישניות **בעצמו**, ושולח לכל חיבור (שחקן/צופה) "תמונת מצב" (snapshot) עדכנית.

נקודה חשובה: `GameSession` לא משתמש ב-`event.EventEngine` הרגיל (זה ששומר "מי נבחר" בשדה יחיד) - כי במשחק מקומי יש עכבר אחד, אבל ברשת יש **שני שחקנים עם בחירות עצמאיות**. אם לבן בוחר כלי, זה לא צריך "לדלוף" לשחור. אז `GameSession` שומר `whiteSelection`/`blackSelection` בנפרד, ומפעיל את אותם כללי-קליק (`event.ClickSelector`) פעם אחת לכל צבע.

### server.Lobby - "מנהל הטורניר"

`Lobby` הוא מי שמחליט **לאיזה** `GameSession` חיבור שייך: פותח חדרים (`createRoom` - יוצר קוד בן 6 תווים), מחבר שחקנים לחדר (`joinRoom`), ומטפל בניתוק/חיבור-מחדש. הוא **לא** משחק בעצמו - הוא רק "מנתב" חיבורים למשחקים הנכונים.

### חשבונות ו-ELO

`server.auth.UserRepository` שומר חשבונות (שם משתמש, סיסמה מוצפנת עם salted SHA-256, דירוג). `server.auth.EloCalculator` הוא נוסחת ELO טהורה וסטטית (K=32, בלי תיקו - כי במשחק הזה תמיד יש מנצח, מלבד "ביטול" משחק בגלל ניתוק שלא סופר בכלל לדירוג). `server.auth.RatingService` מחבר בין השניים - מחשב דירוג חדש ושומר אותו.

## חלק ג': למה בכלל לפצל לתהליכים נפרדים?

הצוות המנחה (בהשראת מערכות אמיתיות בתעשייה) ביקש לבנות את השרת בהשראת ארכיטקטורה של **שירותים נפרדים (microservices)** - כל תהליך אחראי על דבר אחד, אפשר להריץ אותו בנפרד, לעדכן אותו בנפרד, ואם צריך - **להריץ כמה עותקים** ממנו כדי לתמוך ביותר שחקנים (זה בדיוק מה ש-Game Server Shards נותנים).

היתרון המרכזי: אם יש הרבה שחקנים, **תהליך אחד** שעושה הכל בסופו של דבר לא מספיק (יש לו גבול כמה חיבורים/משחקים הוא יכול להחזיק). כשמפצלים לתהליכים נפרדים, כל אחד יכול לרוץ על מחשב אחר, ואפשר להריץ **כמה עותקים** של החלקים ה"כבדים" (כמו Game Server Shard).

המחיר: תהליכים נפרדים לא יכולים "לקרוא ישירות" זה לזה בקוד (`lobby.play(...)`) - הם צריכים לתקשר דרך הרשת (NATS), ומידע שהיה קודם "פשוט זמין" (כמו "מי מחובר") צריך עכשיו להיות **משותף** בצורה מפורשת (Redis).

## חלק ד': ששת הרכיבים - הסבר לעומק

### 1. API Gateway - `server.HttpApiServer` / `server.ApiGateway`

הפעולות ה"לא-חיות" (לא צריכות WebSocket): `POST /api/login`, `POST /api/register`, `POST /api/rooms` (יצירת חדר). כל אלה עוברות REST רגיל, לא WebSocket. `AuthController`/`AuthCommandParser` מטפלים בלוגיקת ההתחברות; `SessionTokenStore` מנפיק "טוקן" (מחרוזת אקראית) שהלקוח שומר ומציג בכל בקשה עתידית במקום לשלוח שם משתמש+סיסמה שוב ושוב.

**`server.ApiGateway`** הוא התהליך העצמאי (בפריסה המבוזרת) - יש לו רק גישה ל-Postgres (חשבונות) ו-Redis (טוקנים), **אין לו** גישה ישירה ל-`Lobby` (כי ה-`Lobby` יושב בתהליך אחר לגמרי, Game Server Shard) - אז יצירת חדר עוברת דרך בקשת NATS (ראו `RoomCreator`/`RemoteRoomCreator` בהמשך).

### 2. WS Gateway - `server.KungFuChessServer`

התהליך שבו **בפועל** נפתח חיבור ה-WebSocket מהלקוח. ההודעה הראשונה חייבת להיות `"attach <token>"` (הטוקן שהתקבל מה-API Gateway). מהרגע הזה, **כל הודעה** מהלקוח (קליק, קפיצה, "play", "join_room") צריכה להגיע ל"מוח" האמיתי של המשחק - אבל ה-WS Gateway **עצמו לא מכיל את המוח הזה יותר** (בפריסה המבוזרת) - הוא רק "ממסר" (relay): לוקח כל הודעה, עוטף אותה במעטפה (`GatewayCommandEnvelope`), ושולח אותה ב-NATS למי שבאמת יודע לטפל בה.

### 3. Matchmaker - `server.Matchmaker` / `server.MatchQueue`

תפקיד אחד ויחיד: **התאמת שחקנים ל"משחק מהיר"** (quick match) לפי דירוג ELO (בטווח ±100). `MatchQueue` היא הלוגיקה הטהורה (תור המתנה, תפוגת זמן אחרי דקה בלי יריב) - **בלי** שום ידיעה על NATS/רשת, כדי שאפשר לבדוק אותה בקלות עם בדיקות אוטומטיות. `server.Matchmaker` הוא התהליך שעוטף אותה ומחבר אותה ל-NATS בפועל.

**חשוב**: Matchmaker **לא** יוצר את המשחק בעצמו - הוא רק מחליט "אלה שני השחקנים שמתאימים", ואז (כפי שנראה בהמשך) שואל את ה-Game Allocator לאיזה shard לשלוח אותם.

### 4. Game Allocator - `server.GameAllocator` / `server.ShardPicker`

**זה הרכיב שהתווסף אחרון, בשלב 6a.** כשיש **יותר משרת-משחק אחד** (Game Server Shard), מישהו צריך להחליט - כל פעם שנוצר room חדש (או שנמצא זיווג ב-quick match) - **לאיזה** shard הוא הולך. `GameAllocator` עונה על השאלה הזאת בצורה הכי פשוטה שיש: **Round-Robin** (תורנות) - shard 1, אז shard 2, אז shard 1, אז shard 2, וחוזר חלילה, בלי לבדוק עומס או שום דבר חכם יותר (זו הייתה החלטה מכוונת - פשטות על פני "חכמה" לא הכרחית בשלב הזה; ראו "מה עוד נשאר" בסוף).

### 5. Game Server Shards - `server.GameServerShard` (כרגע: שניים, `shard-1`/`shard-2`)

זה התהליך שבו **`Lobby`/`GameSession`/`GameEngine` באמת רצים**. כל shard הוא עולם עצמאי משלו - יש לו `Lobby` משלו, עם `rooms` (מפת קוד-חדר → משחק) **משלו**, בזיכרון שלו. shard-1 לא "יודע" שום דבר על חדרים ששייכים ל-shard-2, ולהפך.

### 6. Observability - עדיין לא בוצע

יש רק `logging.ActivityLog` - קובץ טקסט שכל תהליך כותב אליו שורות עם חותמת זמן. אין מטריקות (למשל "כמה משחקים פעילים עכשיו"), אין endpoint לבדיקת תקינות (health check), אין בדיקות עומס.

## חלק ה': הבעיה המרכזית ששלב 6a פתר - ניתוב

ברגע שיש **יותר משרד-משחק אחד**, מתעוררת בעיה אמיתית: ה-WS Gateway מקבל הודעה (למשל "click 3 4") ממחשב של שחקן - **לאיזה shard בדיוק** הוא צריך לשלוח אותה? אם ישלח לשרד הלא נכון, אף אחד לא יטפל בבקשה (או גרוע יותר - **כמה** שרתים ינסו לטפל בה בו-זמנית ויגרמו לבלגן).

הפתרון שנבנה:

1. **כל room מקבל "בעלים"** - כשה-`Lobby` על shard מסוים יוצר room חדש (`createRoom`/`seatMatchedPair`), הוא כותב ל-Redis רשומה: "room הזה שייך לי" (`RoomDirectory`, `roomCode → shardId`).
2. **`join_room <code>`** - ה-WS Gateway, ברגע שהוא רואה פקודת "join_room" עם קוד, שואל את Redis "מי הבעלים של הקוד הזה?" ושולח את הבקשה **ישירות** לשרד הנכון (`shard.<id>.command` - כל shard מאזין רק לנושא NATS **שלו**, לא לנושא משותף).
3. **הודעות המשך (click/jump/rematch)** - ברגע שחיבור "שוייך" לשרד מסוים (על ידי join_room, או זיווג quick-match, או חיבור-מחדש), אותו shard **מודיע** ל-WS Gateway "החיבור הזה שלי מעכשיו" (הודעת NATS קטנה, `conn.<connectionId>.shard`). ה-Gateway שומר את זה בזיכרון שלו (מפה פשוטה, `Map<חיבור, shardId>`), וכל הודעה הבאה מאותו חיבור פשוט הולכת לאותו shard, בלי לשאול את Redis שוב.
4. **"play" (quick match)** - לא צריך שום ניתוב בשלב הבקשה עצמה - הולך תמיד ל-Matchmaker (שהוא תהליך יחיד, בלי sharding בכלל). רק ברגע שנמצא זיווג, Matchmaker שואל את ה-Allocator לאיזה shard לשלוח את שני השחקנים המזווגים.

**נקודה עדינה אחת**: מה קורה אם שחקן **סיים** משחק על shard-1, ואז מבקש `join_room <code2>` שקוד2 שייך ל-shard-2? ה-Gateway **חייב לשאול את Redis מחדש** בכל פעם שמגיעה פקודת join_room (ולא להסתמך על ה-shard ה"ישן" ששמור אצלו מהמשחק הקודם) - אחרת הבקשה תגיע בטעות ל-shard-1 (שלא מכיר בכלל את קוד2) ותיכשל. זו הסיבה ש-`join_room` תמיד "טרי" (ולא סומך על המטמון), בעוד click/jump/rematch **תמיד** סומכים על המטמון (כי הם שייכים למשחק שכבר "שוייך").

## חלק ו': דוגמאות זרימה מלאות (עם המצב הנוכחי - 6a)

### דוגמה 1: התחברות (Login)

```
לקוח                    API Gateway                 Postgres/Redis
  │  POST /api/login          │
  │  (שם משתמש+סיסמה) ───────►│
  │                            │── בודק סיסמה מול Postgres
  │                            │── מנפיק טוקן, שומר ב-Redis
  │◄─── AUTH_OK|token|rating ──│
  │
  │  (מתחבר עכשיו ל-WS Gateway בנפרד, עם WebSocket אמיתי)
  │  attach <token> ──────────► WS Gateway
  │                             │── בודק את הטוקן מול Redis (זהה לכל topology)
  │◄──── AUTH_OK|rating ────────│
```

### דוגמה 2: משחק מהיר (Quick Match) - עם ניתוב מרובה-שרתים

```
לקוח א'          WS Gateway         Matchmaker        Game Allocator      Shard-2
  │  "play" ──────►  │
  │                  │── (אין ניתוב פה בכלל - הכל הולך ל-matchmaker.play)
  │                  │──────────────►  │
  │                  │              (נכנס לתור המתנה)
  │◄── WAITING ───────────────────────│  (Matchmaker שולח בעצמו)

  ... (עובר זמן, שחקן ב' לוחץ "play" גם) ...

  │                  │──────────────►  │── נמצא זיווג! שואל:
  │                  │                 │── "איזה shard?" ───────►  │
  │                  │                 │◄──────── "shard-2" ───────│
  │                  │                 │── שולח shard-2.seat_pair ─────────────►  │
  │                  │                                                            │── יוצר room, מושיב את שניהם
  │                  │◄────── conn.<id-א>.shard = "shard-2" ─────────────────────│ (מודיע ל-Gateway)
  │◄── WELCOME + STATE ── (מגיע דרך conn.<id-א>.out, מ-shard-2 ישירות) ──────────│
```

מעכשיו, ה-Gateway "יודע" ש-חיבור א' שייך ל-shard-2, ושולח לשם כל click/jump עתידי.

### דוגמה 3: קליק במהלך משחק

```
לקוח א' (יודע שהוא ב-shard-2, מהזרימה למעלה)
  │  "click 3 4" ──► WS Gateway
  │                     │── בודק את המטמון: shardOf[חיבור-א'] == "shard-2"
  │                     │── שולח ל- shard-2.command  ──────────► Shard-2
  │                     │                                          │── GameSession מטפל בקליק
  │◄──── COMMAND_RESULT|SUCCESS ─────────────────────────────────│
  │◄──── STATE (מצב מעודכן) ──────────────────────────────────────│
```

### דוגמה 4: יצירת חדר (REST) + הצטרפות חבר

```
יוצר החדר                API Gateway         Game Allocator        Shard-1
  │  POST /api/rooms ──────► │
  │                          │── שואל: "איזה shard?" ──────────►  │
  │                          │◄─────────── "shard-1" ──────────────│
  │                          │── שולח shard-1.create_room ───────────────►  │
  │                          │                                              │── יוצר room, כותב ל-RoomDirectory:
  │                          │                                              │   "ABC123 -> shard-1"
  │◄─ ROOM_CREATED|ABC123 ───│◄────────────── קוד: ABC123 ──────────────────│

חבר (עם הקוד ABC123)         WS Gateway              RoomDirectory (Redis)      Shard-1
  │  "join_room ABC123" ────►   │
  │                              │── שואל: "מי הבעלים של ABC123?" ────►  │
  │                              │◄──────────────── "shard-1" ─────────────│
  │                              │── שולח ל- shard-1.command  ──────────────────────►  │
  │                              │                                                       │── מושיב את החבר, שני
  │                              │                                                       │   השחקנים מקבלים WELCOME+STATE
```

### דוגמה 5: ניתוק והתחברות מחדש

```
שחקן מתנתק (החיבור נסגר בפתאומיות - אינטרנט נפל וכו')
  │  WS Gateway רואה onClose
  │  │── שולח gateway.disconnect (ל**כל** ה-shards - שידור, לא ממוען)
  │  │   רק ה-shard שבאמת מכיר את החיבור הזה עושה משהו; השאר מתעלמים בשקט
  │  │── shard-2 (למשל): מתחיל טיימר של 20 שניות, מודיע ליריב "OPPONENT_DISCONNECTED"

שחקן מתחבר מחדש (טוקן חדש, WebSocket חדש - connectionId חדש לגמרי!)
  │  attach <token> ──► WS Gateway
  │                        │── מזהה שם משתמש, שולח gateway.reconnect (שוב, שידור לכולם)
  │                        │── shard-2 מזהה: "זה שם המשתמש שהיה לי ב-room X!" מבטל את הטיימר,
  │                        │   ומודיע חזרה: conn.<connectionId-חדש>.shard = "shard-2"
  │◄── WELCOME + STATE (המשחק ממשיך בדיוק מאיפה שהוא נעצר) ────────────────────────│
```

שימו לב: שידור `gateway.reconnect`/`gateway.disconnect` **לכל** השרתים (בניגוד ל-`click`/`jump` שהולכים לשרד ספציפי אחד) הוא **בטוח** כי `Lobby.tryReconnect`/`handleDisconnect` על שרד ש"לא מכיר" את המשתמש/החיבור פשוט לא מוצא כלום ולא עושה שום דבר - "לא-פעולה" עדינה, לא שגיאה.

## חלק ז': Docker Compose - כל 9 הקופסאות

```
postgres    - חשבונות + דירוג (קבוע)
redis       - טוקנים, "מי שייך לאיזה room", "מי מחובר-מחדש לאן" (זמני/משותף)
nats        - "לוח המודעות" - כל התקשורת בין התהליכים עוברת דרכו
ws-gateway  - מקבל חיבורי WebSocket מהלקוחות, מנתב הודעות
api-gateway - REST: login/register/create-room
matchmaker  - תור המתנה + התאמת quick-match
game-allocator     - מחליט לאיזה shard הולך room חדש (round-robin)
game-server-shard-1 - מריץ בפועל את המשחקים שהוקצו לו
game-server-shard-2 - כנ"ל, shard שני
```

כולם מוגדרים בקובץ אחד, `docker-compose.yml`, ורצים בפקודה אחת: `docker compose up --build`. הלקוח הגרפי (`NetworkGuiMain`) **לא** רץ ב-Docker בכלל - זה תוכנת שולחן-עבודה רגילה שרצה על המחשב של השחקן, ומתחברת לפורטים החשופים (8887 ל-WebSocket, 8888 ל-REST) - היא אפילו לא "יודעת" שיש כמה shards מאחורי הקלעים.

## חלק ח': מה עדיין נשאר (שלבים 6b ו-6c)

- **Observability (6b)**: היום יש רק לוג טקסט. חסר - מטריקות אמיתיות (כמה משחקים פעילים, כמה שחקנים מחוברים, כמה זמן תגובה), endpoint לבדיקת תקינות (למשל URL שמחזיר "אני חי" לניטור אוטומטי), ובדיקות עומס (load tests - הרצת הרבה "שחקנים מדומים" יחד כדי לבדוק שהמערכת עומדת בעומס).
- **Kubernetes/K3s (6c)**: היום הכל רץ עם Docker Compose - טוב לפיתוח ובדיקה, אבל לא "אמיתי" לסביבת ייצור. Kubernetes הוא כלי לניהול קונטיינרים בקנה מידה גדול (למשל: "אם shard קורס, תרים אחד חדש אוטומטית"; "אם יש הרבה שחקנים, תרים עוד shards לבד"). זה עדיין לא קיים בפרויקט.
- **הקצאה חכמה יותר**: כרגע ה-Allocator עובד round-robin עיוור. שיפור עתידי טבעי (רק אחרי שיהיה Observability) - להקצות room חדש ל-shard שבאמת **הכי פחות עמוס** כרגע, לא סתם "בתור".
